# OpenAPI spec collection

Curated, per-service OpenAPI documents for the Turkish marketplaces that Lonca integrates with.
The collection exists so that:

- developers can read (or generate clients from) a machine-readable definition instead of scraping
  a developer portal;
- the SDKs in [`sdks/`](../sdks/) can be checked against the published contract;
- drift detection ([Vision](../README.md#vision), stage 2) has a tracked baseline to diff live
  responses against: [`pnpm drift`](../packages/drift/) compares the wire shapes recorded by the
  contract probes (`probe-snapshots/`) with the response schemas documented here, and reports
  undocumented fields, missing required fields and type contradictions per operation.
  Properties annotated `x-lonca-observed` / `x-lonca-observed-types` are reported as `known`.

## Layout

```
specs/
  README.md                       ← this file
  <marketplace>/
    README.md                     ← provenance, licence, SDK coverage, known gaps
    manifest.json                 ← index of the files below (generated)
    <service>.json                ← one standalone OpenAPI 3.x document per upstream service
```

- One file per **upstream service**, named after that service as the marketplace itself
  names it, not after the SDK resource that consumes it. On Hepsiburada a service is a host
  (or host + base path): `oms-external`, `mpop-catalog`, ... Trendyol serves everything from
  one host, so there a service is one of the portal's API definitions: `product`,
  `marketplace`, `webhook`, ... n11 also serves everything from one host and publishes no
  definition at all, so there a service is a documentation-portal section: `product`
  ("Ürün Entegrasyonu"), `order` ("Sipariş Entegrasyonu").
- Every file is a self-contained document: `openapi`, `info`, `servers`, `paths` and only the
  `components` its own operations reference. No `$ref` points outside the file.
- Files are generated by a script under [`scripts/specs/`](../scripts/specs/). The raw portal
  capture or dump it reads is **not** tracked in git, because it is large and unreviewed. Small
  hand-maintained inputs, such as Trendyol's `scripts/specs/trendyol/source.mjs` and n11's
  hand-compiled `scripts/specs/n11/source.mjs`, are tracked and reviewed like code. The script is deterministic: paths are sorted, HTTP methods are in
  canonical order, schema names are sorted, and output is 2-space `JSON.stringify` so diffs are
  reviewable. `specs/**/*.json` is excluded from prettier for that reason.
- `x-lonca-*` extension keys carry Lonca's provenance and annotations:
  - `info.x-lonca-source`
  - per-operation `x-lonca-portal-updated-at` and `x-lonca-doc-url`
  - `x-lonca-observed` for anything seen in production but absent from the official
    definition, plus `x-lonca-observed-types` and `x-lonca-guide-example`
  - for hand-compiled definitions (n11): `x-lonca-doc-basis` (field table or example) on
    request bodies and responses, and `x-lonca-doc-example-only` / property-level
    `x-lonca-doc-url` on properties

  Everything else is the upstream definition as captured. Each marketplace README lists its
  exact additions.

## Licence

The API definitions in this directory are the intellectual property of the respective
marketplace operators and are redistributed **unchanged** for interoperability purposes. The
only exceptions are the structural normalisation and the clearly marked additions that each
marketplace README describes. Definitions compiled by hand from a marketplace's own
documentation still describe that marketplace's API and are treated the same way. They are
**not** covered by this repository's MIT licence. If you represent a marketplace and want a
definition removed or corrected, open an issue or contact the maintainers and it will be taken
down promptly.

`scripts/specs/`), READMEs and manifests are Lonca's own work and are MIT-licensed like the rest
of the repository.
